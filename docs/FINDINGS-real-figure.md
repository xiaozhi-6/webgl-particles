# 真实数据上的实测结论（权威版）

> 所有数字都是在**真实生产页面**上测的：43,991 点、900×1200 视口、设备像素 1:1、
> 聚合态。真值是同一页面的 Canvas2D 渲染（`?gl=0`）。
> 这与早先"合成小块"上的标定不同 —— 那些结论**不可用**。

---

|---|---|---|---|

| [0.50,1.00) | 1,519 | 0.74% | **−18.10** |
| [1.00,1.50) | 948 | 0.46% | −11.94 |

- 内容像素的 **98.2% 已饱和**（alpha 落在 240–255）
- 误差集中在占 **2.95%** 的稀疏边缘，那里偏差可达 **−19.66**

## 二、修正倍数的真实需求

按像素 A0 分桶，每个桶取使误差最小的 k：

| A0 区间 | 占比 | 最优 k | 相对 k=1 的改善 |
|---|---|---|---|
| [0.00,0.75) | 1.25% | **k=1.3** | +0.2 ~ +8.9 |
| [0.75,1.50) | 0.95% | **k=1.1** | +7.1 ~ +8.1 |
| [1.50,3.00) | 1.69% | **k=1.05** | +0.4 ~ +1.9 |
| **[3.00,9.00)** | **96.1%** | **k=1** | 0 |

**形状：k 从 1.3（A0→0）单调降到 1.0（A0>3）。**

---

## 三、各方案在真实图形上的实测表现

| 方案 | 平均绝对亮度偏差 |
|---|---|
| 线上 `k = 2.03 − 0.60×(radius/pitch)`（取值 1.58~1.90） | **0.7987** |
| `k = 1`（完全不修正） | **0.5751** |
| `k(A0)` 按点实现（最优标度 a0s=0.2） | **0.5704** |
| 逐桶理想下界（假设能拿到每像素 A0） | 0.4572 |

### 三条结论

**1. 线上的密度修正比不修正更差（0.7987 vs 0.5751，差 39%）。**

它在 A0<3 的桶里确实改善（+0.16 ~ +10.29），但在 A0≥3 的桶里明显变差（−0.29 ~ −0.64），
而后者占 **96% 的像素**。净效果为负。

**2. 修正倍数 1.58~1.90 是在合成小块上标定出来的，那些结论不可用。**

真实图形上需要的最大值只有 **1.3**。

**3. 按"点"给 k 无法兑现"按像素"的理想效果（0.5704 vs 0.4572）。**

原因：一个点覆盖多个像素，给这个点一个 k 会抹平它覆盖像素之间的差异。
理想下界需要**逐像素**的 A0 —— 那需要一次加法混合的 GPU pass 把 A0 场算出来，
再在第二个 pass 里查表。这是两 pass 方案，成本更高，收益只有 0.11/255。

## 四、诚实的总评

| | 结论 |
|---|---|
| 性能问题 | **已解决**：移动端 17fps → 60fps（3 倍） |
| 画质问题 | 密集态**本来就很好**（0.5751/255，92.9% 像素在 ±0.5 内） |
| 线上修正公式 | **是错的**，虽不影响可见效果，但建模方向错了 |
| "无标定解析方案" | **未达成**。闭式模型 `a_gpu = 1-(1-a)^N` 经端到端检验使误差从 5.32 恶化到 16.47 |
| 最诚实的描述 | 这是一个**把性能提升 3 倍、且意外发现原修正公式无依据**的工程案例 |

**所有的偏差都在 1/255 量级**：最大 25（仅出现在 0.65% 的像素上），
绝大多数内容像素的偏差小于 0.5。**肉眼看不出这些差异。**

**项目的真正价值是性能（3 倍），不是画质。** 画质从一开始就基本没问题。

| 选项 | 改动 | 实测收益 | 风险 |

**推荐 A。** 代码更简单、实测更准、无新增开销。B 的额外收益只有 0.11/255，不值得为此引入第二个 pass。
