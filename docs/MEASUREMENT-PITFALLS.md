# 测量陷阱：每一条都曾导致过错误结论

> 这份文档记录本项目的测量方法以及**踩过的所有坑**。
> 里面每一条都曾经把我引向一个错误的结论，写下来是为了别人不用重走。

---

## 1. 一条经验判据

> **两个本应差很多的配置给出相同或反直觉的数字 → 先怀疑测量，不要怀疑物理。**

实际救回过错误的例子：

| 现象 | 真相 |
|---|---|
| 半径 1.5px 与 3.0px 像素面积差 4 倍却**同速** | `gl.finish()` 在 headless 下不同步 |
| 所有档位都恰好 **60fps** | rAF 被 vsync 钳住，无区分度 |
| 半径 **3px 比 1.5px 还快** | `EXT_disjoint_timer_query_webgl2` 返回值不可用 |
| 1,000,000 粒子 = **0.00 ms** | 测到的是命令入队时间 |

**只要数字在物理上讲不通，就先怀疑仪器。**

---

## 2. 读回的语义必须两边一致

比较两套渲染结果时，**必须保证读回的是同一种语义**。

**曾经犯的错**：把 Canvas2D 的 `getImageData`（返回**未预乘**的纯色）
和 WebGL 合成到深底之后的最终像素混着比，得到「未饱和区 WebGL 偏暗 28%」的结论。

| C2D alpha 档 | Canvas2D R | WebGL R | Canvas2D 的 R/(α/255) |
|---|---|---|---|
| [6,64) | 109.87 | 15.12 | **769.54** |
| [64,128) | 103.12 | 37.70 | 280.35 |
| [128,192) | 100.08 | 63.04 | 159.94 |

**归一化后出现 769（超过 255，不可能），立刻暴露了模型用错。**

真相：Canvas2D 返回未预乘的 RGB（≈点色，不随 alpha 变），
而我读 WebGL 侧读的是合成到深底后的结果。
**alpha 本身完全吻合（未饱和区平均差 −0.010）**，差异只出在读取方式。

## 3. 多 program 共享属性槽

**多个 program 共用属性槽时，每次绘制前必须重设全部属性。**

```glsl
// 绘制程序的 0 号槽是 a_corner
// 而 transform feedback 的积分程序 0 号槽是 a_pos
```

积分传递会把 0 号槽改掉 → 绘制时 `a_corner` 读到错误数据
→ **四边形退化成零面积几何 → 0 个像素，且 `glGetError` 返回无错误**。

**这个 bug 伪装成了「性能问题」**（测得 284 ms / 帧），实际是「什么也没画」。

**修法**：

```js
function drawPass(){
  GL.useProgram(DP);
  // 每次绘制前重设 a_corner
  GL.bindBuffer(GL.ARRAY_BUFFER, QB);
  GL.enableVertexAttribArray(LC); GL.vertexAttribDivisor(LC, 0);
  GL.vertexAttribPointer(LC, 2, GL.FLOAT, false, 0, 0);
  ...
}
```

## 4. GPU 计时：三种测法都不可靠

| 测法 | 问题 |
|---|---|
| `gl.finish()` + rAF | headless 下不同步，测到的是命令入队时间 |
| rAF 帧率 | 被 vsync 钳住，所有档位都 60fps |
| `EXT_disjoint_timer_query_webgl2` | 在 Intel UHD + ANGLE/D3D11 下返回值不可用 |

### 可用的测法

```js
// 连续提交多帧，批次末【一次】轻量同步
for (var i = 0; i < BATCH; i++) eng.frame(i * 0.016);
eng.sync();                                  // readPixels 1 个像素
ms = (performance.now() - t0) / BATCH;
```

**要点**：
- 同步点**只读最小的量**（1 个像素，不是全帧）
- 同步**频率远低于帧率**
- **不要在测量循环里造大数据**（一次填 8 MB 的 `Float32Array` 就能把主线程占死）

## 5. 小样本被初始化污染

**任何「每帧成本」的测量，必须先验证它随样本数收敛。**

| 配置 | N=1 | N=5 | N=20 | N=100 | N=200 |
|---|---|---|---|---|---|
| 纯绘制 | 1.0000 | 0.1800 | 0.0500 | 0.0140 | **0.0080** |
| TF 积分 | 1.6000 | 1.4200 | 0.1050 | 0.0610 | **0.0675** |

**差 24 ~ 125 倍。**

用 N=6 的样本除以总时间，测到的是**驱动首次走这条管线的初始化成本**。
曾据此写出「TF 慢 452 倍」的结论 —— **完全错误**。真实净成本是 **+5~19%**。

**做法**：至少跑 warm = 10 / 80 / 160 三档，确认相邻差异 < 25%，**只报稳态值**。

## 6. 输出有效性

**任何性能数字都必须配一个「输出有效性」断言。**

我们曾把 `perMs = 284` 当作「TF 很慢」的证据，
而同一实验里 `inkPixels = 0` —— 那是「什么也没画」。

```js
// 至少做一次：读回有效像素数
var buf = new Uint8Array(W * H * 4);
gl.readPixels(0, 0, W, H, gl.RGBA, gl.UNSIGNED_BYTE, buf);
var ink = 0; for (var i = 0; i < W*H; i++) if (buf[i*4+3] > 6) ink++;
// ink 必须 > 0，否则这个数据点无效
```

**注意**：全帧读回会阻塞主线程，所以只在**最后一档做一次**，不要每帧做。

## 7. 硬件：别在核显上测独显的性能

**双显卡机器上，headless Chrome 默认用核显。**

```
--force_high_performance_gpu
```

| 配置 | 渲染器 |
|---|---|
| 默认 | Intel UHD Graphics（核显） |
| **加 `--force_high_performance_gpu`** | **NVIDIA GeForce GTX 1650 Ti** ✅ |
| 只加 `--use-angle=d3d11` | Intel（无效） |

**本项目的早期 GPU 数据全部是在核显上测的，比独显慢 4~6.6 倍。**

| 粒子数 | 核显 | 独显 | 提升 |
|---|---|---|---|
| 100,000 | 3.755 ms | 0.9400 ms | 4.0× |
| 1,000,000 | 30.425 ms | 6.8525 ms | 4.4× |

**每次运行都要打印 `UNMASKED_RENDERER_WEBGL` 确认跑在哪块卡上。**

## 8. 浏览器：用 Chrome，不要用 Edge

同样的 CDP 工作流：

| 指标 | Edge 154.0.4258 | Chrome 154.0.8037 |
|---|---|---|
| 启动到 CDP 就绪 | ~3000 ms | **469 ms** |
| CDP 往返延迟（10 次） | 经常超时 8~30 秒 | **中位 1 ms / 最大 1 ms** |
| 主线程忙时能否截图 | 不能 | **能** |

**CDP 延迟 1ms vs Edge 动辄超时** —— 这解释了此前大量「页面无响应」的误判。

## 9. CDP 调用必须有超时

**没有超时的 `await` 是一颗定时炸弹。**

```js
// 错误：WebSocket 调用一旦挂起，Node 就永久卡住（不报错、不退出、CPU 为 0）
const send = (method, params) => new Promise(res => {
  const id = ++seq; pending.set(id, { res });
  sock.send(JSON.stringify({ id, method, params }));
});

// 正确：超时也 resolve，绝不挂住
function cdp(method, params = {}, timeoutMs = 15000) {
  return new Promise((resolve) => {
    const id = ++seq;
    const timer = setTimeout(() => {
      pending.delete(id);
      resolve({ __timeout: true });          // 超时也返回
    }, timeoutMs);
    pending.set(id, { resolve, timer });
    sock.send(JSON.stringify({ id, method, params }));
  });
}
```

**再加上硬超时定时器和 `finally` 里的清理**（CDP 连接、浏览器、http 服务）。

## 10. 怎么区分「谁在等」

| 现象 | 含义 |
|---|---|
| 进程 CPU ≈ 0 且不退出 | **宿主在等外部回复** → 查 runner 的超时 |
| 进程 CPU 100% | 页面在算 → 查算法 |
| DOM 和截图都失败 | **主线程被占死** → 查页面里的同步自旋循环 |

**只看「有没有输出」会混淆这些情况，看 CPU 占用率能一眼区分。**

## 12. 「某个配置不行」必须用定罪实验确认

**不能从一处失败推广。**

我们曾经观察到「1,000,000 粒子 / 3.0px 输出为 0、耗时 76 ms」，
差一点写下「填充率墙 + 顶点计算是瓶颈」—— **两个结论都错**。

**定罪实验的做法：固定一切，只改一个变量。**

用**同一套位置缓冲**，只改顶点计算量：

| 顶点计算档 | 中位 (ms) | ink |
|---|---|---|
| V0 零计算 | 14.653 | 1,096,931 |
| V1 一次 sin | 14.447 | 1,070,744 |
| V2 sin+cos+2×fract | 12.253 | 841,592 |

**三个变体全部输出正常，耗时都在 12~15 ms。**
→ 那 0 输出与顶点计算无关，是特定实现路径的 bug。

## 13. 最小探针胜过庞大装置

**两个回合定位根因的对比：**

| 工具 | 规模 | 作用 |
|---|---|---|
| 最小探针 | **8 个粒子** | 直接 `getBufferSubData` 读回，核对写入 |
| 最小端到端 | **6 个粒子** | A/B/C 三组对照，隔离变量 |

**对比之前那些「多档位 × 多模式 × 多变量」的大装置，最小探针快一个数量级。**

**原理**：装置越复杂，状态污染类 bug 越容易被掩盖，也越难定位。
**每次只回答一个问题。**

## 14. 测量脚本的检查清单

发布任何数字之前：

- [ ] **硬件**：打印 `UNMASKED_RENDERER_WEBGL`，确认是哪块卡
- [ ] **浏览器**：Chrome，不是 Edge
- [ ] **收敛**：`per(N)` 随样本数稳定（warm 10/80/160）
- [ ] **输出有效性**：`inkPixels > 0`
- [ ] **重复**：每个配置至少 3 次，取中位
- [ ] **物理自洽**：两个本应差很多的配置，数字确实差很多
- [ ] **读回语义**：两边一致（都未预乘，或都合成后）
- [ ] **属性状态**：多 program 时，每次绘制前重设全部属性
- [ ] **超时**：每个 CDP 调用都有超时；进程有硬超时
- [ ] **清理**：`finally` 里关连接、杀浏览器、停服务

**任何一条不满足，那个数字就不要写进文档。**
