# 从 18fps 到 60fps：4.4 万个粒子如何在手机上跑满帧

我的个人网站首页有一个人物剪影，由 43,991 个半透明小点组成。电脑上一切正常，手机上只剩 18fps。

这篇文章记录我是怎么把它做到 60fps 的。但更要紧的是后面那半段：做到 60fps 之后，我以为自己找到了一个优雅的解析模型来解释两套渲染 API 的差异，结果这个模型被我自己写的检验程序推翻了三次。最后测出来的结论是，**我原来那套看起来有效的修正，比什么都不做还差**。

---

## 一、先把问题定位对

先说结论：**慢的地方不是填充率，是调用开销。**

一开始我也以为是像素太多。把画布的后备存储从 5.60 Mpx 压到 2.1 Mpx，砍掉 62%：

| 设备 | 缓冲区 | 单帧 |
|---|---|---|
| 手机 412×915 | 824×1830 → 618×1373 | 37.2 → 37.8 ms |
| 平板 1024×1366 | 2048×2732 → 1255×1674 | 45.0 → 45.7 ms |

缓冲区少了一半多，耗时没动。

那就换个方向，改点数看线性关系（同一台机器，平板 dpr 2）：

| 绘制点数 | 单帧 |
|---|---|
| 43,991 | 48.4 ms |
| 32,993 | 34.4 ms |
| 21,996 | 23.8 ms |
| 10,998 | 11.7 ms |
| 43,991（只做运动数学，一个点都不画） | 0.76 ms |

每个点约 1.08 µs，纯数学的部分只占一帧的 1.6%。

所以瓶颈是 43,991 次 `beginPath` + `arc` + `fill` 的固定开销。

## 二、试过但没用的几种做法

| 做法 | 结果 |
|---|---|
| Canvas2D `drawImage` 画预渲染精灵 | 116 ms/帧，更慢 |
| Canvas2D `Path2D` 批量合并 | 快 2.8 倍，但一次 `fill` 不逐点叠加，重叠密的地方出现颗粒噪点 |
| WebGL `gl_PointSize` | 快，但小点时点会变大（下面细说） |

`Path2D` 那条特别可惜。它确实把 43,991 次调用合成了一次，快 2.8 倍。但它同时也把 43,991 次源覆盖合成变成了一次。而点云好看的地方恰恰来自那些逐次叠加：密集处会自然堆积到接近实心，稀疏处保持通透。合并之后这个渐变没了，脸上出现明显的颗粒感。

**快和好看在这里是有冲突的。**

## 三、换 WebGL：实例化四边形

`gl_PointSize` 是最省事的做法，一次 `drawArrays(POINTS)` 就画完了，实测单帧快到测不出时间。但画面对不上：

| 状态 | radius (CSS px) | 直径 | dpr 2 下的 `gl_PointSize` | 舍入后 |
|---|---|---|---|---|
| 密集/聚合 | 1.587 | 3.17 | 6.35 | 6（偏小 5%） |
| 散开 | 1.428 | 2.86 | 5.71 | 6（**偏大 5%**） |

`gl_PointSize` 会被实现舍入到整数设备像素。半径小的时候误差方向还反过来，散开态的点肉眼能看出变大，那一态整体亮度高了 24%。

所以改用实例化四边形：每个点画一个四边形，圆在片元着色器里按到中心的距离裁出来，边缘留半个设备像素的过渡带。

```glsl
// 顶点
vec2 pos = a_center + a_corner * a_rad;
vec2 p = pos / u_res * 2.0 - 1.0;
gl_Position = vec4(p.x, -p.y, 0.0, 1.0);
v_local = a_corner;  v_rad = a_rad;

// 片元
float dist = length(v_local) * v_rad;      // 到圆心距离，CSS 像素
float aa   = 0.5 / u_dpr;                  // 半个设备像素
float cov  = clamp((u_rad - dist) / (2.0 * aa) + 0.5, 0.0, 1.0);
if (cov <= 0.0) discard;
outColor = vec4(v_col, cov * v_al);
```

混合方式对齐 Canvas2D 的 source-over：

```js
gl.blendFuncSeparate(gl.SRC_ALPHA, gl.ONE_MINUS_SRC_ALPHA, gl.ONE, gl.ONE_MINUS_SRC_ALPHA);
```

换成实例化四边形之后：

| 设备 | Canvas2D | WebGL2 |
|---|---|---|
| 平板 1024×1366 dpr2 | 57.0 ms（约 18fps） | 16.9 ms（60fps） |
| 手机 412×915 dpr3 | 53.5 ms（约 19fps） | 16.6 ms（60fps） |
| 桌面 1440×900 dpr1 | 本来就满帧 | 本来就满帧 |

3 倍左右。到这一步性能问题算是解决了。

## 四、画面对上了吗

这是我觉得更有意思的部分。

WebGL 刚换上去的时候，画面明显偏暗，还能看出网格感。我量了一下密集区域的收敛颜色（点色 `rgb(120,110,180)`，底色 `#0a0a0a`）：

| 每点 alpha | Canvas2D | WebGL | 比值 |
|---|---|---|---|
| 0.10 | 117.4 | 37.6 | 0.32 |
| 0.20 | 119.8 | 64.4 | 0.54 |
| 0.34 | 120.0（已饱和） | 92.2 | 0.77 |
| 0.50 | 119.2 | 109.2 | 0.92 |
| 1.00 | 120.0 | 120.0 | 1.00 |

Canvas2D 在 alpha 0.34 的时候，密集处就已经被推到满色了；WebGL 要到 1.0 才到同样的值。

原因不复杂：Canvas2D 每次 `fill()` 是一次独立的源覆盖合成，4.4 万次叠下来快速收敛到饱和。而 WebGL 是逐片元累加的。

**所以我当时的想法是：给 WebGL 的 alpha 乘一个修正系数，把两条曲线对齐。**

我确实这么做了，而且看起来很成功。

## 五、那个"很成功"的修正

我搭了一个标定台：铺一块密集的抖动点阵，用 Canvas2D 渲染出参考的收敛色，再二分反解"WebGL 需要用多少 alpha 才能得到同一个颜色"。在好几个密度上跑一遍：

| 半径 / 局部点间距 | 需要的倍数 |
|---|---|
| 0.20（稀疏） | ×1.897 |
| 0.50 | ×1.840 |
| 0.75（密集） | ×1.584 |

倍数随重叠程度单调下降，线性拟合出来是：

```js
k = 2.03 - 0.60 * (radius / localPitch)
alpha_gpu = min(1, baseAlpha * k)
```

`localPitch` 是每个点的局部点间距，点云是静态的，所以初始化时用空间网格数一次邻点就算好了，运行时零开销。

套上去之后，密集状态的逐像素差异从 253 降到 **1.12 / 255**。

我当时觉得这个东西挺漂亮：一个单调的修正曲线，一个有明确物理含义的自变量，零运行时开销，而且效果显著。

**然后我开始怀疑它。**

## 六、三次失败

我对自己那套解释不太满意。它是拟合出来的经验公式，我想找到更根本的东西。

### 第一次：闭式模型

我猜收敛色满足

```
C = 1 - (1-a)^N
```

如果成立，那 WebGL 需要的 alpha 可以直接解出来，完全不需要标定：

```js
a_gpu = 1 - (1-a)^N
```

在合成小块上拟合，看起来完美：单参数拟合 6 个数据点，误差 0.67；交叉验证（用 3 个点拟合、预测另外 3 个点）的均方根误差是 0.46/255，比 8bit 量化步长 1.0 还小。

然后我做了端到端检验：用纯几何公式给出 N（**不拟合任何参数**），渲染出来和 Canvas2D 逐像素比对。

| 方案 | 平均绝对灰度误差 | 最大误差 |
|---|---|---|
| WebGL + 闭式修正 | 16.47 | 46.89 |
| WebGL 原样（完全不修正） | **5.32** | 12.25 |

**修正让画面变差 3 倍。**

问题出在哪我后来才想明白：所谓"交叉验证"，我用的是**自己推导的 N** 去拟合**自己测量的曲线**，而拟合过程中 N 是自由参数，它当然会收敛到误差最小的地方。这不是验证，是拿模型去凑数据然后宣布模型正确。

这件事让我把后面所有的检验都改了规矩：**参数必须由理论给出，然后去预测没参与拟合的数据。**

### 第二次：怀疑是颜色空间

我注意到单点渲染两边其实是完全一致的（跨度 4px、峰值 alpha 255、中心 RGBA 都是 `[255,80,80,255]`），所以差异只可能出在大量点叠加之后的合成环节。那最常见的猜测就是 gamma / 颜色空间。

这个假说很好检验，做一个最小对照就行：不画点，只画一个铺满的矩形。

| alpha | Canvas2D | WebGL | 差 | sRGB 线性模型 |
|---|---|---|---|---|
| 0.02 | 11.67 | 12.33 | 0.67 | 12.53 |
| 0.20 | 35.33 | 35.33 | 0.00 | 35.33 |
| 0.50 | 73.33 | 73.33 | 0.00 | 73.33 |
| 1.00 | 136.67 | 136.67 | 0.00 | 136.67 |

sRGB 线性混合模型的残差和是 **3.27**；如果假设合成发生在线性空间（伽马校正），残差和是 **154.00**。

差两个数量级。

**纯 alpha 合成两边完全一致，在 8bit 精度内逐点差 0。** 颜色空间、伽马、合成方式，全部排除。

### 第三次：在真实图形上重测

到这里我意识到一个更基本的问题：**我之前所有的标定都做在自己搭的合成小块上。**

那些小块的密度分布、子像素相位，都和真实点云不一样。而 `k` 拟合的是真实点云上的平均效应。这个错配可能就是问题。

所以我在真实页面上重做了一遍：把页面里的 Canvas2D 渲染当真值，给 WebGL 加一个 URL 参数直接覆盖修正倍数，然后扫一遍。

结果是这样（43,991 点、900×1200 视口、聚合态）：

| 方案 | 平均绝对亮度偏差 |
|---|---|
| 我那套 `k(density)`（取值 1.58~1.90） | **0.7987** |
| `k = 1`（完全不修正） | **0.5751** |

**比什么都不做还差 39%。**

## 七、为什么

我把误差按"每像素的基础 alpha 累积"（记作 A0）分桶看，就清楚了：

| A0 区间 | 占比 | Canvas2D vs WebGL（k=1） |
|---|---|---|
| [0.00,1.00) | 1.39% | −19.7 / −18.1 |
| [1.00,2.50) | 1.56% | −11.9 ~ −2.2 |
| **[3.50,8.00)** | **96.9%** | **−0.03 ~ +0.04** |

两件事：

**一、误差几乎全在稀疏区。** 92.9% 的内容像素偏差在 ±0.5 以内。真正偏得多的，是占 2.95% 的稀疏边缘，那里 WebGL 比 Canvas2D 暗 19 个单位。

**二、内容像素里 98.2% 已经饱和了。** 饱和之后 `1-(1-a)^N ≈ 1`，和 `a` 无关，所以 `k` 取任何值结果都一样。而 `k(density)` 在占 96% 的密集区反而把误差从 0.18 抬到 0.48。

真实需要的修正倍数，按 A0 分桶是这样的：

| A0 区间 | 占比 | 最优 k |
|---|---|---|
| [0.00,0.75) | 1.25% | 1.3 |
| [0.75,1.50) | 0.95% | 1.1 |
| [1.50,3.00) | 1.69% | 1.05 |
| [3.00,9.00) | 96.1% | 1 |

**最大只要 1.3，而我在合成小块上标出来的是 1.6~1.9。**

我也试过按点给一个 `k(A0)`，用真实测出的这条曲线。效果是 0.5704，比不修正的 0.5751 只好 0.005，等于没有。原因是一个点覆盖多个像素，给这个点一个 `k` 会把它覆盖的那些像素之间的差异抹平。要做到理想（0.4572）必须逐像素算 A0，那需要额外一个加法混合的 pass。

**为了 0.11/255 再引入一个 GPU pass，不划算。**

## 八、最后的处置

我把那个修正整个删了，连带删掉只服务于它的 `localPitch` 网格计算。代码少了 1975 字节，少一次初始化循环。

| | 平均绝对亮度偏差 | 偏差 >40 的像素 |
|---|---|---|
| 删之前 | 0.7987 | — |
| 删之后 | **0.5751** | **0.11%** |

移动端帧时没变（平板 16.7 ms，手机 16.6 ms）。

三语 × 六尺寸、功能（外链、复制、标签页切换）全部回归通过，0 异常。

## 九、真正的教训

**一、别在自己造的合成数据上标定，然后拿去解释真实数据。**

我三次犯错都跟这个有关。合成小块和真实点云在密度分布、子像素相位上都不一样，在小块上量出的"需要放大 1.6~1.9 倍"，在真实数据上只到 1.3。

**二、"交叉验证误差小于量化步长"也可能是自欺。**

如果参数是拟合出来的，把同一批数据再喂回去，误差当然小。检验只能是：参数由理论给出，去预测没参与拟合的数据。

**三、负结果要留下来。**

三次失败里，只有第一次是真的错。第二次（颜色空间）和第三次（密度效应）虽然假说被否，但**排除过程本身就是结论**：现在我可以确定地说，Canvas2D 和 WebGL 的纯 alpha 合成在 8bit 精度内完全一致，差异只来自**圆的覆盖率如何被光栅化**。

**四、要算收益的量级。**

我花了很久在 1/255 量级的事情上。而这套东西真正的价值是性能：3 倍，从 18fps 到 60fps。画质从一开始就基本没问题（92.9% 的像素偏差在 ±0.5 以内）。

**我以为自己在修一个 60~90% 的偏差，其实只在修一个 5~7% 的平均偏移，而且只发生在 3% 的像素上。**

## 十、代码

`webgl-particles`：一个约 400 行、零依赖的 ES module，把点云从 Canvas2D 的逐点 `arc+fill` 换成 WebGL2 实例化四边形，带自动回退。

- 仓库：https://github.com/xiaozhi-6/webgl-particles
- 在线 demo：https://xiaozhi-6.github.io/webgl-particles/demo/
- 完整测量数据（包括所有失败路径）：`docs/TECHNICAL.md`、`docs/FINDINGS-real-figure.md`

如果你也在做类似的东西，这个项目里我认为最有用的是两件事：

1. **实例化四边形 + 片元算覆盖率**，绕开 `gl_PointSize` 的整数舍入
2. **上面那些否掉假说的最小对照实验**，它们能省掉你自己重新走一遍的时间

至于那套 alpha 修正，**别用**。
