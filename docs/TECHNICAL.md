# 技术说明：实测数据、根因分析、走过的弯路

README 讲怎么用。这里放实测数据、根因分析和走不通的路。

被测量对象是 **43,991 个半透明圆点组成的剪影**，基线实现是 Canvas2D 逐点
`beginPath` + `arc` + `fill`。

> **本文所有数字都标注了测量条件。凡是没能复现或后来被推翻的，都保留在文里并写明原因。**

---

## 1. 慢在哪里：调用开销，不是填充率

### 1.1 各种方案的单帧耗时

| 方案 | 单帧 | 结果 |
|---|---|---|
| Canvas2D 逐点 `arc` + `fill` | 32 ~ 54 ms | 基线 |
| Canvas2D `drawImage` 画精灵 | ~116 ms | 更慢，放弃 |
| Canvas2D `Path2D` 批量合并 | ~15 ms（2.8 倍） | 重叠处有颗粒噪点，放弃 |
| WebGL2 `gl_PointSize` 点精灵 | ~0.01 ms | 整数栅格化，小点时点会被放大，放弃 |
| **WebGL2 实例化四边形** | **0.1 ~ 1.9 ms** | 采用 |

### 1.2 怎么量的

把人物层单独隔离出来，停掉同页其他动画消耗者，只量它的 rAF 帧间隔。
平板 1024×1366、dpr 2、滚动状态下：

| 后端 | 中位 | p90 |
|---|---|---|
| Canvas2D | 48.6 ~ 57.0 ms（约 17 ~ 20 fps） | 59 ~ 63 ms |
| WebGL2 | 16.7 ~ 16.9 ms（60 fps） | 17 ~ 20 ms |

### 1.3 排除填充率

压后备存储的像素量，从 5.60 Mpx 压到 2.1 Mpx，减了 62%：

| 设备 | 缓冲区 | 单帧 |
|---|---|---|
| 手机 412×915 | 824×1830 → 618×1373 | 37.2 → 37.8 ms |
| 平板 1024×1366 | 2048×2732 → 1255×1674 | 45.0 → 45.7 ms |

缓冲区少了一半多，耗时没动。说明开销来自每个点的固定调用，不来自像素填充。

## 2. 观感对齐：从 253.74 到 1.12

### 2.1 两个必须先解决的语义差异

**一、`gl_PointSize` 会被舍入到整数设备像素。**

半径 1.5 设备像素的点，`gl_PointSize` 只能给 1 或 2，看起来会明显变胖或变瘦。
改用**实例化四边形 + 片元按距离算覆盖率**，亚像素精确。

**二、两个光栅化器的边缘过渡带不一样宽。**

Canvas2D 的 `arc` 在边缘约 1 个设备像素里完成过渡；片元里手写的过渡带如果不匹配，
边缘会明显更硬或更软。

### 2.2 覆盖率函数

线上的公式：

```glsl
float dist = length(v_local) * v_rad;
float aa   = 0.5 / u_dpr;
float cov  = clamp((v_rad - dist) / (2.0 * aa) + 0.5, 0.0, 1.0);
```

**这个线性过渡带是经过比较后留下的最优选择。** 试过的替代方案见 §5。

## 3. 四边形扩边 0.5 像素（唯一的正向改动）

### 3.1 问题

原来的顶点是：

```glsl
vec2 pos = a_center + a_corner * a_rad;   // 恰好只覆盖 ±a_rad
```

**落在圆周上的片元正好位于四边形边界，按填充规则不会被光栅化 → 边缘少一整圈覆盖率。**

### 3.2 修复

```glsl
vec2 pos = a_center + a_corner * (a_rad + 0.5);
v_local  = a_corner * (a_rad + 0.5) / a_rad;   // 保持 ±1 对应 a_rad 的语义
```

扩 0.5 与 1.0 的实测结果**完全相同**，说明收益来自「让边缘片元被光栅化」，
不是「多覆盖多少」。**顶点数不变（仍是 4 个），无性能开销。**

### 3.3 验收（宽屏 1440×900 dpr1，以 Canvas2D 为真值）

| 方案 | 平均 alpha | 亮度平均差 | 最大差 | >10 占比 |
|---|---|---|---|---|
| Canvas2D | 252.8900 | — | — | — |
| 不扩边 | 252.4768 | 0.77429 | 141.2 | 2.454% |
| **扩边 0.5** | **252.7560** | **0.54266** | **84.5** | **1.565%** |

**改善 29.9%**，且 alpha 更接近 Canvas2D。分子集：

| 子集 | n | 不扩边 | 扩边 0.5 | 改善 |
|---|---|---|---|---|
| 饱和（alpha ≥ 250） | 188,927 | 0.40809 | **0.21539** | **−47.2%** |
| 未饱和（< 240） | 3,888 | 17.66420 | **15.74733** | −10.9% |

窄屏 1024×1366 dpr2 场景：0.32944 → **0.26008**（改善 21.1%），
alpha 从 253.7736 → 253.8224，**与 Canvas2D 的 253.8230 差 0.0006**。

## 5. 走过的弯路（全部实测否定，别重走）

### 5.1 按密度修正 alpha —— ⛔ **已从代码中移除**

**这条曾写进实现思路，是错的。**

做法是按「半径 / 局部点间距」把 alpha 放大：

```js
k = 2.03 - 0.60 * (radius / localPitch)     // 实测 1.90（疏）→ 1.58（密）
```

**在真实图形上实测：**

| 方案 | 平均绝对亮度差 |
|---|---|
| 不做修正 | **0.5751** |
| 按密度修正 | 0.7987（**差 39%**） |

**原因**：这个模型假设「点均匀分布」，而真实剪影的边缘和内部密度差异极大，
用局部间距推出来的倍数在边缘过冲、在内部不足。

**代码里已经删除，只留下注释说明为什么不要做。**

### 5.2 精确面积覆盖 / 超采样（SS4 / SS8）

线性过渡带在单点层面确实偏高：对精确圆-像素交集面积，**偏差 +3.90%**，
而 SS8 只有 −0.97%，**逐相位误差小 2.7 倍**。

**但在真实图形上换上去反而更差：**

| 方案 | 平均绝对亮度差 |
|---|---|
| **线性过渡带（采用）** | **0.3345** |
| SS4 | 0.4434（差 32.5%） |
| SS8 | 0.4175（差 24.8%） |

三者的 **alpha 总量几乎完全相同**（252.97 / 252.93 / 252.92）——
换覆盖率只改变了 alpha 的分布，而新分布更差。

**结论：「Canvas2D = 精确面积覆盖」这个模型是错的**，而线性过渡带恰好更接近 Skia 的真实行为。

### 5.3 闭式解析模型 `1-(1-a)^N`

端到端实测否定：**5.32 → 16.47**（更差）。

### 5.4 颜色空间 / 伽马

**严格排除**：残差 **3.27** vs 假设伽马错误时的 **154.00**。

### 5.5 alpha 合成方式

**严格排除**：逐像素差 **0.00**。

### 5.6 Canvas2D 用硬阈值光栅化

**排除**：Canvas2D 输出里有 **59 种**不同的中间 alpha 值。

## 6. 测量本身踩过的坑

这一节的每一条都曾导致过错误结论。

### 6.1 `readPixels` 的语义

1. **读回是空白** —— WebGL canvas 默认 `preserveDrawingBuffer: false`。
   要么创建时开这个选项，要么用 `drawImage` 拷进 2D canvas 再读。

2. **原点在左下，Canvas2D 在左上** —— 逐像素比对必须翻转 y，
   不翻转会得到约 **87% 的假差异**。

3. **`drawImage(glCanvas, 0, 0)` 的尺寸语义** —— 源用它的后备像素尺寸，
   目标是当前变换下的尺寸。2D context 已经 `setTransform(dpr, ...)` 时，
   先 `setTransform(1,0,0,1,0,0)` 再按 1:1 拷贝最稳。

4. **要等 `gl.finish()` 之后再 `drawImage`**，否则可能拷到没画完的帧。

### 6.2 两套渲染结果比较时的读回语义

**必须保证两边读回的是同一种语义。**

曾经把 Canvas2D 的 `getImageData`（返回**未预乘**的纯色）
和 WebGL 合成到深底之后的最终像素混着比，得到「未饱和区 WebGL 偏暗 28%」的结论 ——
**那是测量假象**。

| C2D alpha 档 | Canvas2D R | WebGL R | Canvas2D 的 R/(α/255) |
|---|---|---|---|
| [6,64) | 109.87 | 15.12 | **769.54**（超过 255，不可能） |
| [64,128) | 103.12 | 37.70 | 280.35 |

**归一化后超过 255 立刻暴露了模型用错。** alpha 本身完全吻合（未饱和区平均差 **−0.010**）。

### 6.3 多 program 共享属性槽

**多个 program 共用属性槽时，每次绘制前必须重设全部属性。**

`a_corner` 在绘制程序里是 0 号槽，而 transform feedback 的积分程序也用 0 号槽读 `a_pos`。
积分传递会把 0 号槽改掉 → 绘制时四边形退化成零面积几何 → **0 个像素，且 `glGetError` 返回无错误**。

**这个 bug 伪装成了「性能问题」**（测得 284 ms），实际是「什么也没画」。

### 6.4 GPU 计时

| 测法 | 问题 |
|---|---|
| `gl.finish()` + rAF | headless 下不同步，测到的是命令入队时间（曾得出「100 万粒子 = 0.00 ms」） |
| rAF 帧率 | 被 vsync 钳住，所有档位都 60fps，无区分度 |
| `EXT_disjoint_timer_query_webgl2` | 在 Intel UHD + ANGLE/D3D11 下返回值不可用（3px 比 1.5px 还快、两模式差 2147 倍） |

**可用的测法**：连续提交多帧后**一次** `readPixels(1 像素)` 强制同步，
取总时间除以帧数。同步点只读最小的量。

### 6.5 小样本被初始化污染

**任何「每帧成本」的测量，必须先验证它随样本数收敛。**

| 配置 | N=1 | N=200 |
|---|---|---|
| 纯绘制 | 1.0000 ms | **0.0080 ms** |
| TF 积分 | 1.6000 ms | **0.0675 ms** |

**差 24 ~ 125 倍。** 用 N=6 的样本除以总时间，测到的是驱动首次走这条管线的初始化成本。
曾据此写出「TF 慢 452 倍」的结论 —— **完全错误**。

### 6.6 硬件

**`--force_high_performance_gpu`** —— 双显卡机器上，headless Chrome 默认用核显。
本项目的早期 GPU 数据全部是在 Intel UHD 核显上测的，比独显（GTX 1650 Ti）**慢 4~6.6 倍**。

### 6.7 浏览器

**用 Chrome，不要用 Edge。** 同样的 CDP 工作流：

| 指标 | Edge 154.0.4258 | Chrome 154.0.8037 |
|---|---|---|
| 启动到 CDP 就绪 | ~3000 ms | **469 ms** |
| CDP 往返延迟 | 经常超时 8~30 秒 | **中位 1 ms** |
| 主线程忙时能否截图 | 不能 | **能** |

### 6.8 输出有效性

**任何性能数字都必须配一个「输出有效性」断言。**

我们曾把 `perMs = 284` 当作「TF 很慢」的证据，而同一实验里 `inkPixels = 0`
—— 那是「什么也没画」。**加一个读回有效像素数的检查就能立刻发现。**

### 6.9 一条经验判据

> **两个本应差很多的配置给出相同或反直觉的数字 → 先怀疑测量，不要怀疑物理。**

- 半径 1.5px 与 3.0px 像素面积差 4 倍却**同速** → 测量错
- 所有档位都恰好 **60fps** → vsync 钳制
- 3px 比 1.5px **还快** → timer query 不可用

这条判据在整个研究过程中救回过多次错误结论。

## 7. GPU 批量渲染的成本结构

> 这一节的数据来自 `docs/FINDINGS-gpu-cost.md`，**硬件是 NVIDIA GTX 1650 Ti**，
> 画布 1800×1200 设备像素，每档均通过收敛性与输出有效性检查。

### 7.1 成本公式

```
每帧成本 ≈ 填充率项 + 顶点/组织项
填充率项 ∝ π × 半径² × 粒子数     （受画布边界裁剪）
顶点/组织项 ≈ 每粒子 5 ~ 8 ns      （与半径无关）
```

### 7.2 实测：半径是主导因素

固定 500,000 粒子，四种顶点计算量（L0 零计算 → L3 最重）× 四个半径：

| 顶点计算档 | 半径 1.0 | 半径 1.5 | 半径 2.0 | 半径 3.0 |
|---|---|---|---|---|
| L0 零计算 | 3.090 | 4.178 | 5.518 | 8.033 |
| L1 1×sin | 2.940 | 4.037 | 5.300 | 7.780 |
| L2 sin+cos+2×fract | **2.740** | **3.757** | **4.923** | **7.152** |
| L3 2×sin+2×cos+2×fract | 2.962 | 4.063 | 5.338 | 7.720 |

（单位 ms）

- **半径 1.0 → 3.0：覆盖像素涨 9 倍，耗时涨 2.6 倍** → 填充率是主导
- **L0 与 L3 只差 7~10%**（且 L2 最快、L0 最慢，说明落在噪声内）→ 顶点计算量不是瓶颈

### 7.3 实测：逐实例属性基本免费

1,000,000 粒子，唯一变量是半径的分布，平均半径都 = 2.0：

| 配置 | 实际均半径 | 每帧 | 每粒子 |
|---|---|---|---|
| A 全部半径相同 | 2.000 | 8.080 ms | 8.08 ns |
| B 半径随机 ±1.0 | 1.986 | **7.780 ms** | 7.78 ns |
| C 半径随机 ±1.75 | 1.985 | **8.007 ms** | 8.01 ns |

**差异在噪声内。** 实例化架构对「每粒子独立属性」几乎无成本 ——
因为实例化的本质就是「每实例一份属性」。

### 7.4 实测：有状态积分的成本

用 transform feedback 做 ping-pong 状态积分（每粒子 16 字节读写）：

| 粒子数 | 半径 | 纯绘制 | TF 积分 | 净成本 |
|---|---|---|---|---|
| 100,000 | 1.5 | 1.045 ms | 1.205 ms | **+15%** |
| 500,000 | 1.5 | 4.245 ms | 4.7875 ms | +13% |
| 1,000,000 | 1.5 | 6.855 ms | 8.1425 ms | +19% |

**净成本 5% ~ 19%，每粒子约 1.0 ~ 1.6 ns。**

### 7.5 规模上限

| 粒子数 | 半径 1.5px | 半径 3.0px |
|---|---|---|
| 100,000 | 1.045 ms | 1.8275 ms |
| 500,000 | 4.245 ms | 7.9875 ms |
| **1,000,000** | **6.855 ms（≈146fps）** | ~12 ~ 15 ms |

**100 万粒子、两种半径，都在 60fps（16.7 ms）预算内。**

墙由 **密度指标**（半径² × 粒子数 / 画布面积）决定，不是单一变量：

| 画布（设备像素） | 50 万 | 100 万 | 200 万 | 每粒子 |
|---|---|---|---|---|
| 900×600 | 2.42 | 4.37 | 8.30 | 4.84 ns |
| 1800×1200 | 4.11 | 6.88 | 11.22 | 8.22 ns |
| 2800×1800 | 4.31 | 7.13 | 12.51 | 8.62 ns |
| 3600×2400 | 4.49 | 8.45 | **76.74** | 8.98 ns |

**画布面积 ×4，耗时只涨 1.8~1.9 倍** —— 再次说明不是纯填充率。
**每粒子成本在 1800×1200 以上趋于平坦（≈8.6~9.0 ns）。**

### 7.6 实测：连线在百万级不可行

连线是「元素间关系」，它天然不是实例化的。每条边实例化一个四边形：

| 粒子数 | 边数 | 每帧 | 每边 |
|---|---|---|---|
| 100,000 | 600,000 | 12.63 ms | **21.04 ns** |
| 500,000 | 3,000,000 | 53.77 ms | **17.92 ns** |

**每条边 18~27 ns，比渲染一个圆形粒子（6.9~8.5 ns）还贵 2~3 倍。**

| 目标 | 边数 | 预估 | 60fps |
|---|---|---|---|
| 10 万粒子 × 6 边 | 60 万 | 10.8~16.2 ms | ⚠️ 卡满预算 |
| 50 万粒子 × 6 边 | 300 万 | 53.8~77.3 ms | ❌ |
| 100 万粒子 × 6 边 | 600 万 | 108~162 ms | ❌ |

**60 万条边就吃满了全部帧预算。连线不在本项目的适用范围内。**
