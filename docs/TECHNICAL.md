# 技术说明

README 讲怎么用。这里放实测数据、根因分析、标定过程和走不通的路子。

被测对象是 43,991 个半透明圆点组成的剪影，基线实现是 Canvas2D 逐点
`beginPath` + `arc` + `fill`。

---

## 1. 慢在哪：调用开销，不是填充率

### 1.1 各种方案的单帧耗时

| 方案 | 单帧 | 结果 |
|---|---|---|
| Canvas2D 逐点 `arc` + `fill` | 32 ~ 54 ms | 基线 |
| Canvas2D `drawImage` 画精灵 | ~116 ms | 更慢，放弃 |
| Canvas2D `Path2D` 批量合并 | ~15 ms（2.8 倍） | 重叠处有颗粒噪点，放弃 |
| WebGL2 `gl_PointSize` 点精灵 | ~0.01 ms | 整数栅格化，小点时点会被放大，放弃 |
| **WebGL2 实例化四边形** | **0.1 ~ 1.9 ms** | 采用 |

### 1.2 怎么量的

把人物层单独隔离出来，停掉同页其它动画消费者，只量它的 rAF 帧间隔。
平板 1024×1366、dpr 2、滚动状态下：

| 后端 | 中位 | p90 |
|---|---|---|
| Canvas2D | 48.6 ~ 57.0 ms（约 17 ~ 20 fps） | 59 ~ 63 ms |
| WebGL2 | 16.7 ~ 16.9 ms（60 fps） | 17 ~ 20 ms |

### 1.3 排除填充率

压后备存储的像素量，从 5.60 Mpx 压到 2.1 Mpx，减了 62%：

| 设备 | 缓冲区 | 单帧 |
|---|---|---|
| 手机 412×915 | 824×1830 → 618×1373 | 37.2 → 37.8 ms |
| 平板 1024×1366 | 2048×2732 → 1255×1674 | 45.0 → 45.7 ms |

缓冲区少了一半多，耗时没动。说明开销来自每个点的固定调用，不来自像素填充。

再改点数看线性关系（同一台机器，平板 dpr 2）：

| 绘制点数 | 单帧 |
|---|---|
| 43,991 | 48.4 ms |
| 32,993 | 34.4 ms |
| 21,996 | 23.8 ms |
| 10,998 | 11.7 ms |
| 43,991（只算数学，一个点都不画） | 0.76 ms |

每个点约 1.08 µs，纯数学的部分占一帧的 1.6%。

## 2. 画面对不上的原因：Canvas2D 的 alpha 会饱和

### 2.1 单个点其实是完全一致的

隔离环境里画一个点，两种后端的结果：

| | 水平跨度 | 纵向跨度 | 峰值 alpha | 中心 RGBA |
|---|---|---|---|---|
| Canvas2D | 4 px | 4 px | 255 | `[255,80,80,255]` |
| WebGL | 4 px | 4 px | 255 | `[255,80,80,255]` |

几何、颜色、alpha 数值全对得上。差异只出现在大量点叠加之后的合成环节。

### 2.2 密集覆盖区的实测颜色

铺满一块区域的均匀密集点阵，点色 `rgb(120,110,180)`，底色 `#0a0a0a`：

| 每点 alpha | Canvas2D | WebGL | 比值 |
|---|---|---|---|
| 0.10 | 117.4 | 37.6 | 0.320 |
| 0.20 | 119.8 | 64.4 | 0.538 |
| **0.34** | **120.0（已饱和）** | 92.2 | 0.768 |
| 0.50 | 119.2 | 109.2 | 0.916 |
| 0.75 | 120.0 | 118.9 | 0.991 |
| 1.00 | 120.0 | 120.0 | 1.000 |

Canvas2D 每次 `fill()` 是一次独立的源覆盖合成，4.4 万次叠下来，密集区域在 alpha 0.34
就推到满色了。WebGL 是逐片元累加，要 alpha 1.0 才到同一个颜色。

画面一开始偏暗、能看出网格感，原因就在这里。

### 2.3 试过但没关系的方向

| 方向 | 结论 |
|---|---|
| `gl_PointSize` 整数舍入 | 确实存在（见第 3 节），但只能解释小半径时点变大 |
| 颜色空间 | `colorSpace:'srgb'` 和 `desynchronized` 实测都没差别 |
| `drawImage` 尺寸语义 | 是我测试台自己写错了，改对之后没差别 |
| `readPixels` 读回 | 默认 `preserveDrawingBuffer: false`，读到的是空白。测试台得用 `drawImage` 拷进 2D canvas 再读 |

## 3. `gl_PointSize` 的问题

实现会把它舍入到整数设备像素。

| 状态 | radius（CSS px） | 直径 | `gl_PointSize`（dpr 2） | 舍入后 |
|---|---|---|---|---|
| 密集/聚合 | 1.587 | 3.17 | 6.35 | 6（偏小 5%） |
| 散开 | 1.428 | 2.86 | 5.71 | 6（偏大 5%） |

半径小的时候误差方向还反过来，散开态的点肉眼能看出变大，实测该状态亮度高了 24%。

换成实例化四边形之后，圆在片元着色器里按距离裁，边缘留半个设备像素的过渡带，
两种状态都能对上。

## 4. 标定密度与 alpha 修正倍数

### 4.1 方法

固定颜色和 DPR，改点间距 `pitch` 和半径 `rad`，先用 Canvas2D 渲染一块作为参考收敛色，
再二分反解「WebGL 用多少 alpha 才能得到同一个收敛色」。

### 4.2 标定结果

| pitch | rad | 密度 /100px² | rad/pitch | 所需 alpha | 倍数 k |
|---|---|---|---|---|---|
| 5.0 | 1.0 | 396.9 | 0.20 | 0.645 | **×1.897** |
| 4.0 | 1.2 | 605.6 | 0.30 | 0.645 | ×1.897 |
| 4.0 | 1.5 | 605.6 | 0.38 | 0.626 | ×1.840 |
| 3.5 | 1.5 | 791.0 | 0.43 | 0.626 | ×1.840 |
| 3.0 | 1.5 | 1076.7 | 0.50 | 0.626 | ×1.840 |
| 3.0 | 1.8 | 1076.7 | 0.60 | 0.594 | ×1.747 |
| 2.5 | 1.5 | 1556.6 | 0.60 | 0.590 | ×1.736 |
| 2.5 | 1.8 | 1556.6 | 0.72 | 0.551 | ×1.621 |
| 2.0 | 1.5 | 2422.5 | 0.75 | 0.538 | **×1.584** |

倍数主要由 `rad/pitch`（重叠程度）决定，密度的影响小得多，整体从 ×1.90 单调降到 ×1.58。
线性拟合，代码里钳制在 `[1.0, 2.4]`：

```js
k = 2.03 - 0.60 * (radius / localPitch)
```

### 4.3 `localPitch` 的算法

初始化时跑一次：

```js
// 用空间网格统计半径 2.5×radius 内的邻点数 cnt
// 每个点占的面积约等于 π r² / cnt，等效方形间距就是它的平方根
localPitch[i] = cnt > 1 ? Math.sqrt(Math.PI * r2 / cnt) : r;
```

点云是静态的，这一步只在初始化跑，运行时没有开销。

有一点要留意：**探测半径得跟着该状态的实际点半径走**。散开态半径缩到 0.9 倍、
点云铺满全屏，如果还用密集态的探测半径，邻点数会少算，等效间距偏小，
修正倍数就偏大，画面跟着偏亮。

### 4.4 效果

同一套数据、同一个状态：

| | 逐像素平均差 | 差异超过 40 的像素 |
|---|---|---|
| 修正前 | 253.74 | 100% |
| 修正后 | **1.12 / 255** | **0.28%** |

## 6. 踩过的坑

1. **`readPixels` 读回是空白。** WebGL canvas 默认 `preserveDrawingBuffer: false`。
   要么创建时开这个选项，要么用 `drawImage` 拷进 2D canvas 再读。

2. **`readPixels` 原点在左下，Canvas2D 在左上。** 逐像素比对必须翻转 y，
   不翻转会得到约 87% 的假差异。

3. **`drawImage(glCanvas, 0, 0)` 的尺寸语义。** 源用它的后备像素尺寸，
   目标是当前变换下的尺寸。2D context 已经 `setTransform(dpr, ...)` 时，
   先 `setTransform(1,0,0,1,0,0)` 再按 1:1 拷贝最稳。

4. **要等 `gl.finish()` 之后再 `drawImage`**，否则可能拷到没画完的帧。

5. **别拿同一套 GL 程序和缓冲去画不同批量。** 属性状态会串。
   标定和主渲染各建一套。

6. **`Path2D` 批量虽然快 2.8 倍，但一次 `fill` 不会逐点叠加**，重叠密的地方会有颗粒噪点，
   要保观感就不能用。

7. **降分辨率对这类负载没用**，见 1.3。

8. **统计函数里别忘 `getContext('2d')`。** `canvas.getImageData` 不存在。

## 7. 还能往下做的

过渡阶段目前还有 8~23% 的亮度偏差，按可能性排：

1. **把密度分档做细。** 现在是单一线性拟合。散开态的点云是随机分布，
   局部间距的分布比标定用的规则网格宽得多，一个均值描述不了。
   可以按 `localPitch` 分 8~16 档，每档一条曲线。

2. **把标定搬到运行时。** 在 `requestIdleCallback` 里用 Canvas2D 渲染一小块标定板，
   反解当前参数下的 `k` 曲线。米哈游官网有类似时段的调度做法。

3. **按进度分档。** 过渡过程中半径和色调都在变。初始化时对 4~8 个进度档各算一套
   `localPitch → k` 表，运行时线性插值。

4. **用 `WEBGL_lose_context` 回收上下文。** 页面长时间不可见时主动释放，
   降低移动端的内存压力。`destroy()` 里已经实现了。
