# 技术说明：全部实测数据、根因与标定

本文是 `point-figure` 的完整技术档案。README 讲怎么用，这里讲**为什么这么做**、
**数据是多少**、**哪些路走不通**。

---

## 1. 性能：瓶颈在调用开销，不在填充率

被测对象：43,991 个半透明圆点的剪影，Canvas2D 逐点 `beginPath` + `arc` + `fill`。

### 1.1 单帧渲染耗时

| 方案 | 单帧 | 结论 |
|---|---|---|
| Canvas2D 逐点 `arc`+`fill` | **32 ~ 54 ms** | 基准 |
| Canvas2D `drawImage` 精灵 | ~116 ms | 更慢，否决 |
| Canvas2D `Path2D` 批量合并 | ~15 ms（2.8×） | 重叠处出现颗粒噪点，否决 |
| WebGL2 `gl_PointSize` 点精灵 | ~0.01 ms | 整数栅格化 → 小点时点变大，否决 |
| **WebGL2 实例化四边形** | **0.1 ~ 1.9 ms** | ✅ 采用 |

### 1.2 掉帧的定位方法

把「人物层」单独隔离出来量 rAF 帧间隔（停掉同页其它动画消费者），
在平板 1024×1366 dpr2 上滚动：

| 后端 | 中位 | p90 | 帧率 |
|---|---|---|---|
| Canvas2D | **48.6 ~ 57.0 ms** | 59 ~ 63 ms | ≈17 ~ 20 fps |
| WebGL2 | **16.7 ~ 16.9 ms** | 17 ~ 20 ms | **60 fps** |

### 1.3 为什么不是填充率

按「缓冲区像素量」压分辨率（像素预算法），把后备存储从 5.60 Mpx 压到 2.1 Mpx（−62%）：

| 设备 | 缓冲区 | 单帧 |
|---|---|---|
| 手机 412×915 | 824×1830 → **618×1373** | 37.2 → 37.8 ms |
| 平板 1024×1366 | 2048×2732 → **1255×1674** | 45.0 → 45.7 ms |

**缓冲区砍掉一半以上，耗时几乎不变** → 瓶颈是**每点的固定调用开销**，不是像素填充。

点数与耗时的关系**完全线性**（同一台机器，平板 dpr2）：

| 绘制点数 | 单帧 |
|---|---|
| 43,991 | 48.4 ms |
| 32,993 | 34.4 ms |
| 21,996 | 23.8 ms |
| 10,998 | 11.7 ms |
| 43,991（只做数学、完全不画） | **0.76 ms** |

→ **每点 ≈ 1.08 µs，数学只占 1.6%。**

## 2. 画面对不上的根因：Canvas2D 的 alpha 会「饱和」

这是整个项目最关键的一节。

### 2.1 单点渲染其实完全一致

隔离环境画**一个**点，两种后端：

| | 水平跨度 | 纵向跨度 | 峰值 alpha | 中心 RGBA |
|---|---|---|---|---|
| Canvas2D | 4 px | 4 px | 255 | `[255,80,80,255]` |
| WebGL | 4 px | 4 px | 255 | `[255,80,80,255]` |

**完全一致。** 所以差异不在几何、颜色或数值，只在**大量点叠加后的合成**。

### 2.2 密集覆盖区的实测色

密集均匀点阵（覆盖满一块区域），点色 `rgb(120,110,180)`，深底 `#0a0a0a`：

| 每点 alpha | Canvas2D | WebGL | 比值 |
|---|---|---|---|
| 0.10 | 117.4 | 37.6 | 0.320 |
| 0.20 | 119.8 | 64.4 | 0.538 |
| **0.34** | **120.0 ← 饱和** | 92.2 | 0.768 |
| 0.50 | 119.2 | 109.2 | 0.916 |
| 0.75 | 120.0 | 118.9 | 0.991 |
| 1.00 | 120.0 | 120.0 | 1.000 |

**Canvas2D 在 alpha=0.34 时密实处就已被推满色**，WebGL 要到 1.0。
因为 Canvas2D 的每一次 `fill()` 都是一次独立的源覆盖合成，4.4 万次叠加快速收敛；
而逐个点精灵/四边形的混合是逐片元线性累积的。

**这就是「WebGL 画面偏暗、像网格空壳」的唯一原因。**

### 2.3 排除掉的其它嫌疑

| 嫌疑 | 验证结果 |
|---|---|
| `gl_PointSize` 整数舍入 | **是真的**（见 §3），但只解释小半径时的点变大 |
| 颜色空间 | `colorSpace:'srgb'`、`desynchronized` 实测**无差别** ❌ |
| `drawImage` 尺寸语义 | 我的测试台曾写错，修正后无差别 ❌ |
| `readPixels` 读回 | 默认 `preserveDrawingBuffer:false` 会读到空白 → 测试台必须用 `drawImage` 拷回 2D canvas 再读 |

## 3. 为什么不能用 `gl_PointSize`

`gl_PointSize` 会被实现**舍入到整数设备像素**。

| 状态 | radius (CSS px) | 直径 | `gl_PointSize`(dpr2) | 舍入后 |
|---|---|---|---|---|
| 密集/聚合 | 1.587 | 3.17 | 6.35 | 6（误差 −5%） |
| 散开 | 1.428 | 2.86 | 5.71 | 6（误差 **+5%**，点变大） |

小半径时误差方向还相反，导致散开态的点**明显变大**（实测散开态亮度 +24%）。

**改用实例化四边形**后，圆由片元着色器按距离裁出，边缘是半个设备像素的过渡带，
**亚像素精确**，两种状态都对得上。

## 4. 标定：密度 → alpha 修正倍数

### 4.1 标定方法

固定颜色与 DPR，改变点间距 `pitch` 与半径 `rad`，用 Canvas2D 渲染一块得到「参考收敛色」，
再二分反解 **WebGL 需要多少 alpha 才能得到同一个收敛色**。

### 4.2 实测标定表

| pitch | rad | 密度 /100px² | rad/pitch | 所需 alpha | **倍数 k** |
|---|---|---|---|---|---|
| 5.0 | 1.0 | 396.9 | 0.20 | 0.645 | **×1.897** |
| 4.0 | 1.2 | 605.6 | 0.30 | 0.645 | ×1.897 |
| 4.0 | 1.5 | 605.6 | 0.38 | 0.626 | ×1.840 |
| 3.5 | 1.5 | 791.0 | 0.43 | 0.626 | ×1.840 |
| 3.0 | 1.5 | 1076.7 | 0.50 | 0.626 | ×1.840 |
| 3.0 | 1.8 | 1076.7 | 0.60 | 0.594 | ×1.747 |
| 2.5 | 1.5 | 1556.6 | 0.60 | 0.590 | ×1.736 |
| 2.5 | 1.8 | 1556.6 | 0.72 | 0.551 | ×1.621 |
| 2.0 | 1.5 | 2422.5 | 0.75 | 0.538 | **×1.584** |

**规律：倍数由 `rad/pitch`（重叠程度）主导，密度只占次要**，
从 ×1.90 单调降到 ×1.58。线性拟合（已钳制到 `[1.0, 2.4]`）：

```js
k = 2.03 - 0.60 * (radius / localPitch)
```

### 4.3 `localPitch` 怎么算（离线一次）

```js
// 网格加速：统计半径 2.5×radius 内的邻点数 cnt
// 每点占面积 ≈ π r² / cnt  →  等效方形间距 = sqrt(π r² / cnt)
localPitch[i] = cnt > 1 ? Math.sqrt(Math.PI * r2 / cnt) : r;
```

点云是静态的，所以这一步**只在初始化跑一次，运行时零开销**。

> ⚠️ **探测半径必须与该状态的实际点半径成比例**。
> 散开态半径缩到 0.9 倍、点云摊到全屏，若沿用密集态的探测半径，
> 邻点数会少算 → 等效间距偏小 → 修正倍数偏大 → 画面偏亮。

### 4.4 套用后的提升

同一套数据、同一状态：

| | 逐像素平均差 | 差异 >40 的像素 |
|---|---|---|
| 修正前 | 253.74 | 100% |
| **修正后** | **1.12 / 255** | **0.28%** |

## 6. 踩过的坑（别再犯）

1. **`readPixels` 默认读到空白** —— WebGL canvas 默认 `preserveDrawingBuffer: false`。
   要么创建时开 `preserveDrawingBuffer: true`，要么用 `drawImage` 拷进 2D canvas 再读。
2. **`readPixels` 原点在左下**、Canvas2D 在左上。
   逐像素比对**必须翻转 y**，否则会得到 ~87% 的假差异。
3. **`drawImage(glCanvas, 0, 0)` 的尺寸语义**：
   源用其**后备像素**尺寸，目标是**当前变换下**的尺寸。
   2D context 已 `setTransform(dpr,...)` 时，先 `setTransform(1,0,0,1,0,0)` 再 1:1 拷贝最稳。
4. **必须等 `gl.finish()` 之后再 `drawImage`**，否则可能拷到未完成的帧。
5. **别复用同一套 GL 程序/缓冲做不同批量的绘制** —— 属性状态会串。
   标定与主渲染各建一套。
6. **`Path2D` 批量虽然快 2.8×，但一次 `fill` 不会逐点叠加**，
   重叠密的地方会出现颗粒噪点。**追求观感时不可用。**
7. **降分辨率（像素预算）对这类负载无效** —— 见 §1.3。
8. **统计函数里别忘 `getContext('2d')`**（`canvas.getImageData` 不存在）。

## 7. 后续可做的优化

当前过渡态仍有 8~23% 亮度偏差。按嫌疑排序：

1. **更细的密度分档标定**
   现在用单一线性拟合。散开态的点云是**随机分布**，其「局部间距分布」比标定用的
   规则网格更宽，单一均值不足以描述。可以按 `localPitch` 分 8~16 档各建一条曲线。

2. **把标定搬到运行时（可选）**
   在 `requestIdleCallback` 里用 Canvas2D 渲染一小块标定板，
   反解当前参数下的 `k` 曲线，做自适应。米哈游用 `requestIdleCallback` 做类似调度。

3. **按 `pt` 分档**
   过渡态半径与 `mix` 都在变。可以在初始化时对 4~8 个 `pt` 档各算一套
   `localPitch → k` 表，运行时线性插值。

4. **`WEBGL_lose_context` 回收**
   页面长时间不可见时主动释放 GL 上下文，降低移动端内存压力（`destroy()` 已实现）。
